    Criterion 1

    Business value proposition

    Why a company would pay for precision retrieval, and the measured proof behind each promise.

    Slide 3 · problem

    The problem: an LLM answers from whatever it is given

    What goes wrong in naive RAG

    • The search returns passages that look similar but answer a different question; the LLM then answers confidently from the wrong text.
    • Policies change. If an old version stays in the index, the assistant quotes a refund window that no longer applies.
    • Departments need answers from their own documents only, without a second system.
    • GPU servers and paid APIs make a pilot expensive before it has proven anything.

    Who feels it

    • Customer support: refund, shipping and warranty questions answered from current policy.
    • HR and internal help desks: leave and remote-work rules, scoped to internal documents.
    • Knowledge search: large document sets where look-alike passages are common.

    Diagram file: docs/diagrams/business-naive-vs-precision.svg

    Retrieval decides what the LLM reads. We made the right passage come first, kept only the current version of every document, and let the user scope the search — on hardware a company already has.

    To 10 million passages (plan, not measured)

    At the measured ≈ 4.4 KB per passage, 10M passages need about 42 GB before compression. Qdrant's int8 scalar quantization keeps compressed vectors in RAM and the originals on disk; sharding spreads the collection over machines.

    What stays constant

    The reranker reads a fixed number of candidates (10 or 20), so its cost does not grow with the corpus. Updates touch one point each; nothing is ever rebuilt.

    Criterion 3

    Solution architecture

    How the pieces fit, why each was chosen, and what we tried and rejected.

    Slide 10 · architecture

    System overview

    Diagram file: docs/diagrams/architecture-system.svg

    Indexing writes both vector types and the metadata into one Qdrant collection. One API serves search, answers, updates and the dashboard; the web UI and any company system use the same endpoints.

    Slide 11 · query path

    Query path: one round trip, then a short rerank

    Diagram file: docs/diagrams/architecture-query-pipeline.svg

    Dense and BM25 searches go to Qdrant in one batched request, with the filter applied inside both. Fusion is rank-based, and the cross-encoder reads only the short list.

    results/latency/*.json → median_stage_ms

    Slide 12 · data

    Data model and filters

    Diagram file: docs/diagrams/architecture-data-model.svg

    Topic tags were computed from the vectors already stored (100k passages in 83 s, no re-embedding). Pre-filtering happens inside the HNSW search, so a filtered query still returns 5 results.

    Slide 13 · updates

    Live update path

    Diagram file: docs/diagrams/architecture-live-updates.svg

    The point ID is derived from the document ID, so an update overwrites the old version instead of adding a copy. The change log keeps every version for audit.

    Backup · Q&A

    The 30 hardest judge questions

    1 · Why Qdrant, not pgvector, Weaviate or ChromaDB?Dense + BM25 sparse (server-side IDF) in one collection, filtered HNSW for real pre-filtering, payload indexes, batched queries, native Windows binary.
    2 · Why bge-small, not a bigger embedder?Strong retrieval at 384-d and fast on both CPU and GPU; 100k passages index in 21.59 min on the CPU. The reranker buys the precision.
    3 · Why not OpenAI or a hosted database?Free tier only, and only Qdrant, Weaviate, ChromaDB or pgvector are allowed. Everything runs locally.
    4 · Why run 100k on CPU and 500k on GPU?It shows both ends: any laptop serves 100k at 140 ms p95; a small laptop GPU serves 5× more at 76 ms.
    5 · Why is the GPU at 500k faster than the CPU at 100k?The reranker: 78 ms for 10 passages on CPU, 30 ms for 20 on GPU. Qdrant search only goes 18 → 22 ms.
    6 · The baseline already beats 0.75. What did Phase 2 add?MRR +0.062 at 500k (CI +0.042 … +0.083); RAGAS precision 0.754 → 0.820 at 500k; +0.048 MRR at 100k on CPU.
    7 · Hybrid ≈ dense. Why keep BM25?It is required, and it widens the reranker's pool: at 500k, top-20 pool 89.9% → 93.1%.
    8 · Why weighted RRF, not linear fusion?No score normalisation. Linear won on tuning (0.541) but not on test (0.533).
    9 · How was the BM25 weight 0.1 chosen?A grid on 1,000 tuning questions; more weight hurt (0.494 at 1 : 1).
    10 · Why rerank only the top 10 or 20?Top-30 gave the same MRR as top-20 on tuning (0.598 vs 0.598); the CPU reads 10 to stay fast.
    11 · Did you tune on the test set?No. Disjoint frozen sets: tune on dev_large, confirm once on test; when test disagreed we kept the simpler setting.
    12 · Is an LLM judge reliable?Same judge, temperature 0, same questions for every mode; the 1,000-question label metrics point the same way.
    13 · RAGAS intervals include zero. Is the gain real?50 questions is small; the proof is the 1,000-question label metric, whose interval excludes zero.
    14 · Why not non-LLM RAGAS metrics?String similarity scored a water passage as correct for an ethanol question.
    15 · The reranker was trained on MS MARCO. Unfair?It has a home advantage; we say so and would validate or fine-tune it on company data.
    16 · How was p95 measured?100 consecutive questions through the HTTP API, cache off, 5 warm-ups: CPU 100k p50 110 / p95 140 ms; GPU 500k 65 / 76 ms.
    17 · What if the CPU is busy?Re-measured while OneDrive synced the project, CPU p95 rose to 532 ms. The CPU deployment needs a quiet machine; the GPU one was not affected.
    18 · What about 10M passages?≈ 4.4 KB per passage measured; int8 quantization, originals on disk, sharding. The reranker's cost stays fixed.
    19 · How long does indexing take?21.59 min for 100k on the CPU, 13.3 min for 500k on the GPU (limit 120), resumable.
    20 · Pre-filter or post-filter?Pre: inside Qdrant's request, in both searches, on indexed fields, so there are always 5 matching results.
    21 · What if the user picks the wrong filter?The answer can be filtered out, which is why automatic routing lost −0.067 MRR. “Any” stays the default; topics are suggested.
    22 · How is stale data prevented?ID = UUID5(doc_id) overwrites; index_version is part of the cache key; the change log keeps history.
    23 · What does an update cost?37–84 ms per write in the scripted demo; Qdrant updates the graph and BM25 statistics incrementally.
    24 · Can I see what changed?Yes: before / after answers, a word diff and the version history on the Live Updates page.
    25 · How accurate are the topic tags?70% agree with an LLM judge, 82% within our top 2; a correct topic filter adds +0.074 MRR.
    26 · Why not route queries automatically?Measured −0.067 MRR on test with the top-2 guess (84.1% routed right).
    27 · How did you stay within the free LLM tier?Evaluation runs are resumable; a failed judge call is retried later, never saved as a zero.
    28 · Where does it still fail?Look-alike passages, gaps in the labels, unanswerable questions; 39 of 1,000 fail in every mode at 100k.
    29 · Can anyone reproduce this?One command per number, 154 pinned packages, frozen question sets, 48 tests, report generated from results/.
    30 · What would you do next?Access-control filters, domain fine-tuning of embedder and reranker, quantization for 10M+, answer-faithfulness monitoring.

    Backup

    Measurement notes

    • Deployment pairing used throughout: 100k on the CPU profile (reranker top 10), 500k on the GPU profile (top 20).
    • Latency for both deployments was measured back to back in one session (2026-10-03).
    • The CPU deployment shares the processor: re-measured while OneDrive synced the folder, Phase 2 p95 was 532 ms.
    • The 500k build took 13.3 min on an idle machine (results/build_index_500k.log); a later rebuild that shared the GPU took 16.79 min.
    • RAGAS at 100k on the CPU: dense and hybrid give exactly the same top-5 passages as the GPU for all 50 questions (results/ragas/cpu_vs_gpu_contexts_100k.json), so those scores are shared. Phase 2 on the CPU was scored separately: 0.809 / 0.900.
    • Tuning curves (fusion weight, rerank depth) were measured once on the 1,000 tuning questions to choose settings.
    • First search after ~10 s idle is slower on the laptop GPU (power saving); consecutive use is unaffected.
